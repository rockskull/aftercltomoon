# AFTER CL TO MOON — 클럽 웹사이트

석촌호수 근처 사설 볼더링 클럽 **AFTER CL TO MOON**의 모바일 우선 웹사이트(PWA)입니다.
멤버는 일정과 회원권을 확인하고 이벤트를 제안합니다. 운영진은 **관리 화면(ADMIN)** 에서 일정·회원·회비·설정을 관리하고, 입금만 확인·승인하면 회원권 기간과 알림이 자동으로 처리됩니다. 데이터는 **Postgres 데이터베이스(Neon, Vercel Storage)** 에 저장됩니다(2026-11-13 Google Sheets에서 이전).

> **이어서 작업할 때는 [docs/HANDOFF.md](docs/HANDOFF.md) 체크리스트부터 보세요.**

- **v0.1** 월간 캘린더(멤버 등록기간 / 이벤트 신청기간 / 이벤트), 이벤트 목록·상세, 이벤트 제안서
- **v0.2** Google 로그인, 회원권(기간 자동 계산·연장), 모임통장 입금 승인, 거래내역 엑셀 매칭, 운영진 화면, PWA 설치, 웹 푸시 알림
- **추가** 동의서, 회계 장부, 초대장(`/invite`), 이벤트 포스터 생성기(MAKE A POSTER), MOON STAMPS, 회원권 달 단위(1일 시작 · 말일 종료), AFTER HOURS RADIO(`/radio`)

## 구조

```
브라우저(PWA) ──▶ Next.js 16 (Vercel) ──▶ Postgres (Neon · Vercel Storage)
                     │  서버에서만 DB 접근 (DATABASE_URL)
                     │  로그인·권한 매 요청 검증
                     └─ Vercel Cron ──▶ /api/cron/notifications ──▶ Web Push
```

- **정본은 데이터베이스입니다.** 예전 시트의 탭마다 같은 이름·같은 열의 테이블이 하나씩 있습니다(`members`, `payments`, `radio_tracks` …, 값은 모두 text, 행 순서는 `_seq`). 운영진은 시트 대신 관리 화면에서 편집하고, 꼭 필요하면 Neon 콘솔의 표 편집기로 직접 볼 수 있습니다.
- **쓰기는 모두 `commit` 하나로 처리합니다.** 한 트랜잭션 안에서 잠금(`pg_advisory_xact_lock`)을 잡고 ① 같은 요청의 재시도인지 확인(AuditLog의 `commit_id`)하고 ② 전제조건을 실시간 데이터로 다시 검증한 뒤 ③ 쓰기 전체를 검사하고 ④ 씁니다. 이 구조로 같은 입금의 중복 승인, 동시 승인으로 인한 기간 겹침, 네트워크 재시도로 인한 중복 반영을 막습니다. 규칙은 `src/server/store/commit.ts` 한 곳에 있고, DB(`postgres.ts`)와 데모용 메모리 저장소가 함께 씁니다.
- **공개 일정에는 공개된 것만 나갑니다.** `visibility=public` 이고 `status`가 published/closed/canceled인 이벤트와 공개 열만 씁니다(`src/server/store/public-feed.ts`). 회원·회비·제안·구독 정보는 서버 안에서만 읽습니다.
- 저장소는 환경변수로 정해집니다: `DATABASE_URL`이 있으면 DB, 없고 `CLUB_API_URL`+`CLUB_API_SECRET`이 있으면 예전 시트(Apps Script), 둘 다 없으면 데모. 시트 방식 코드(`apps-script/`)는 이전용으로만 남겨 두었습니다.

### 데이터베이스 (Neon)

- `npm run db:status` — 연결된 DB와 테이블별 행 수(비밀값은 출력하지 않음)
- `npm run db:migrate` — 테이블을 만들고 시트 데이터를 한 번에 복사(트랜잭션, 행 수 검증). DB에 데이터가 있으면 멈추고, `-- --replace`는 **DB로 전환하기 전에만** 다시 복사할 때 씁니다.
- `npm run db:compare` — 시트와 DB의 내용이 같은지 읽기만 해서 비교(표별 행 수·내용 해시)
- DB 통합 테스트(임시 스키마를 만들었다 지움): `DB_TEST=1 npx vitest run postgres.integration`
- ⚠️ `.env.local`에 `DATABASE_URL`이 있으면 **로컬 `npm run dev`도 실제 DB를 씁니다.** 로컬에서 마음껏 시험하려면 Neon에서 개발용 브랜치를 만들어 그 주소를 쓰거나, `.env.local`에서 `DATABASE_URL`을 빼고 데모로 실행하세요.

## 로컬에서 실행

```bash
npm install
npm run dev        # http://localhost:3000
```

환경변수가 없으면 **데모 모드**로 실행됩니다. 예시 일정과 예시 회원이 서버 메모리에 만들어지고, `/login`에서 데모 계정(운영진, 이용 중 회원, 곧 만료 회원, 입금 대기 신청자, 미등록 계정)을 골라 모든 화면을 확인할 수 있습니다.

```bash
npm test           # 단위 테스트(기간 계산, 승인 동시성, 거래내역 파서, 알림 스케줄 등)
npm run lint
npm run typecheck
npm run build
npm run secrets    # Vercel·Apps Script용 비밀값을 vercel-env.secret.txt(Git 제외)에 생성
npm run ledger:convert -- "<회비 사용 내역.xlsx>"   # 기존 장부 → private/ledger-import.xlsx (Git 제외)
```

> **시트를 연결하기 전에는 배포된 사이트도 자동으로 데모 모드**로 동작합니다. 상단에 데모 배너가 뜨고, 로그인 화면에서 데모 계정(운영진 포함)을 골라 회원·관리 화면을 둘러볼 수 있습니다. 데모 데이터는 서버 메모리에만 있어 수시로 초기화되고, 제안서에 적은 연락처는 저장하지 않습니다. `CLUB_API_URL`과 `CLUB_API_SECRET`을 넣으면 데모는 자동으로 꺼집니다. 시트 연결 전에 회원 기능을 아예 숨기려면 `DEMO_MODE=false`로 설정하세요.

## 배포 순서

### 1. 스프레드시트와 Apps Script

1. Google 드라이브에서 새 스프레드시트를 만듭니다. 운영진에게만 편집 권한을 공유합니다.
2. **확장 프로그램 → Apps Script**를 열고 `apps-script/Code.gs` 내용을 붙여넣습니다. 프로젝트 설정에서 시간대를 `Asia/Seoul`로 맞춥니다(또는 `appsscript.json` 내용을 사용합니다).
3. 편집기에서 **`setupSheets`** 함수를 한 번 실행합니다(처음에 권한 승인 필요). 탭 17개, 머리글, 드롭다운, 기본 회원권 상품 3종, MOON STAMPS 4종(ST-05·06은 정의 행이 없어도 코드 기본값으로 보임), 라디오 기본곡 14곡, 설정 값이 만들어지고 시트 시간대가 서울로 바뀝니다. 다시 실행해도 기존 데이터는 그대로 두고 빠진 열만 추가합니다.
   > **Apps Script를 아직 실행할 수 없다면** `apps-script/after-cl-to-moon-sheet-template.xlsx`로 같은 시트 구조를 만들 수 있습니다.
   > Google Sheets에서 **파일 → 가져오기 → 업로드 → 스프레드시트 바꾸기**로 가져온 뒤 **파일 → 설정 → 시간대**를 `(GMT+09:00) 서울`로 맞추고, Settings 탭의 `sheet_url`에 시트 주소를 붙여넣으세요.
   > 나중에 Apps Script에서 `setupSheets`를 실행해도 기존 데이터는 그대로 두므로 안전합니다.
4. **프로젝트 설정 → 스크립트 속성**에 다음 값을 추가합니다.
   - `PROPOSAL_SECRET`: 긴 무작위 문자열. Vercel의 `CLUB_API_SECRET`과 같은 값입니다.
   - `SITE_URL`: `https://<사이트 주소>` (15분 알림 트리거 `Tick.gs`를 쓸 때)
   - `CRON_SECRET`: Vercel의 `CRON_SECRET`과 같은 값 (15분 알림 트리거 `Tick.gs`를 쓸 때)
5. **배포 → 새 배포 → 웹 앱**으로 배포합니다. 실행 계정은 **나**, 액세스 권한은 **모든 사용자**로 설정하고, 발급된 `/exec` URL을 `CLUB_API_URL`로 씁니다.
   *코드를 고친 뒤에는 배포 관리 → 수정 → 새 버전으로 다시 배포해야 하며, URL은 그대로 유지됩니다.*
6. (선택) 편집기에서 **+ → 스크립트**로 `Tick` 파일을 추가해 `apps-script/Tick.gs`를 붙여넣고 **`installTick`**을 실행하면 15분마다 알림 스케줄러가 호출됩니다. 이벤트 신청 시작·마감 알림이 더 제때 나갑니다.
   *`Code.gs`는 `@OnlyCurrentDoc`으로 이 스프레드시트 하나에만 접근합니다. `Tick.gs`는 외부 서비스 연결·사용자 부재 시 실행 권한을 추가로 요청하므로, 확인되지 않은 앱 승인이 차단되는 계정에서는 넣지 않습니다(Vercel Cron이 하루 한 번 호출).*
7. **Settings 탭**의 `apply_notice`(회원권 신청 후 안내 문구)를 확인합니다. **계좌번호와 금액은 사이트에 넣지 않습니다.** 회비 금액과 입금 계좌는 회원 등록 동의서와 크루 단톡방으로 안내합니다(아래 "사이트에서 결제를 요청하지 않는 이유" 참고).

### 2. Google 로그인

1. [Google Cloud Console](https://console.cloud.google.com/) → API 및 서비스 → **OAuth 동의 화면**을 구성합니다(외부, 범위 `openid email profile`).
2. **사용자 인증 정보 → OAuth 클라이언트 ID**를 만듭니다. 유형은 **웹 애플리케이션**입니다.
   - 승인된 리디렉션 URI: `https://<사이트 주소>/api/auth/callback/google` (로컬 테스트용으로 `http://localhost:3000/api/auth/callback/google`도 추가)
3. 클라이언트 ID와 비밀번호를 `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`에 넣습니다.

### 3. 웹 푸시 키

```bash
npx web-push generate-vapid-keys
```
공개 키는 `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, 개인 키는 `VAPID_PRIVATE_KEY`에 넣습니다. `VAPID_SUBJECT`에는 `mailto:운영진메일`을 씁니다. 키를 바꾸면 기존 구독이 모두 무효가 되니 한 번 정하면 유지합니다.

### 4. Vercel

GitHub 저장소를 Vercel 프로젝트로 가져온 뒤, **Settings → Environment Variables**에 `.env.example`의 값을 설정하고 배포합니다.

| 변수 | 필수 | 설명 |
|---|---|---|
| `CLUB_API_URL` | ✓ | Apps Script 웹앱 `/exec` URL |
| `CLUB_API_SECRET` | ✓ | 스크립트 속성 `PROPOSAL_SECRET`과 같은 값 |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | ✓ | Google 로그인 |
| `AUTH_SECRET` | ✓ | 32자 이상 무작위 문자열(세션 서명). 데모 모드에서는 없어도 동작하지만, 시트를 연결하면 필수 |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` | 푸시 | 없으면 앱 안 알림 목록만 동작 |
| `CRON_SECRET` | ✓ | 스케줄러 호출 인증(Vercel Cron이 자동으로 첨부) |
| `NEXT_PUBLIC_SITE_URL` | | 공유 미리보기용 주소(기본값: Vercel 운영 도메인) |
| `DEMO_MODE` | | 시트가 없으면 기본이 데모 모드. `false`로 두면 시트 연결 전까지 회원 기능을 "준비 중"으로 숨김 |

`vercel.json`의 Cron이 **매일 09:00(KST)**에 `/api/cron/notifications`를 호출합니다. Hobby 요금제의 Cron은 하루 한 번만 실행되므로, 더 촘촘한 알림이 필요하면 1-6의 Apps Script 트리거를 함께 씁니다. 두 쪽이 겹쳐 실행돼도 중복 발송되지 않습니다.

### 5. 첫 운영진 지정

Members 탭에 직접 한 줄을 추가합니다.

| member_id | name | email | depositor_name | role | status |
|---|---|---|---|---|---|
| M-ADMIN-1 | 이름 | 운영진의 Google 메일 | 입금자명 | admin | active |

이후 운영진 권한은 웹의 **ADMIN → 회원 → 상세**에서 admin만 바꿀 수 있습니다.

**admin과 운영자(operator)의 차이** (`src/lib/permissions.ts` 한 곳에서 정하고, 관리 화면 탭·각 화면·서버 처리·운영진 알림이 모두 이것을 따릅니다)

| 할 수 있는 일 | admin | operator |
|---|---|---|
| 관리 화면 접근, 회원 목록·상태(단톡방 확인) 보기 | ✓ | ✓ |
| 이벤트·등록 기간, 제안 검토 | ✓ | ✓ |
| AFTER HOURS RADIO 트랙 관리(순서·이름·메모·삭제·복원) | ✓ | ✓ |
| MOON PROBLEMS 문제 등록·수정·보관·삭제, 후기 숨기기 | ✓ | ✓ |
| 설정 → 아지트 공지 | ✓ | ✓ |
| 회원 스탬프 발급·발급 취소 | ✓ | ✓ |
| 입금 확인·승인·반려·환불, 거래내역, 회계, 회원권 등록 계산·직접 등록·기간 수정 | ✓ | ✗ |
| 회원 추가, 회원 정보·상태·권한 수정 | ✓ | ✗ |
| 회원권 상품, 사이트 설정(신청 안내·동의서 링크·라디오 플레이어), 스탬프 이름·설명 | ✓ | ✗ |

- operator에게는 입금 확인·회계·거래내역 탭이 보이지 않고 주소로 들어가도 404입니다. 회원 상세에서는 회원 정보가 읽기 전용이고, 회원권 수정·등록·회비 칸이 없습니다(스탬프 칸은 있음). 화면을 우회해 돈 관련 처리를 보내도 서버가 거절합니다.
- 입금 대기 알림은 admin에게만 가고, operator의 하루 운영 요약에는 입금 건수 없이 만료 예정 인원만 들어갑니다.

## 운영 가이드

### 일정 (Events / Enrollment 탭)

- **이벤트는 ADMIN → 이벤트에서 등록·수정합니다.** 저장하면 Events 탭에 기록되고 캘린더에 바로 반영됩니다(변경 이력은 AuditLog). 시트에서 직접 고쳐도 되며, 그 경우 사이트에는 1~2분 뒤 보입니다. 다른 사람이 그사이 같은 이벤트를 고쳤다면 저장이 멈추고 최신 내용을 다시 불러옵니다. 모집 공고(Enrollment)는 아직 시트에서 입력합니다.
- **확정된 제안 → 이벤트:** ADMIN → 제안에서 상태를 "진행 확정"으로 바꾸면 **이벤트로 옮기기** 버튼이 생깁니다. 누르면 제목·설명·주최·대상이 채워진 등록 폼이 제안 내용(희망 날짜, 인원, 필요한 것)과 함께 열리고, 날짜·시간을 정해 등록하면 됩니다. 이벤트 ID는 `EV-<제안 ID>`가 되어 같은 제안을 두 번 옮길 수 없고, 제안 목록에서 연결된 이벤트로 바로 갈 수 있습니다.
- 화면의 "상태"는 아래 `status`, "사이트 공개"는 `visibility`입니다. 이벤트는 지우지 않고 `canceled`(취소)나 `draft`(초안)로 바꿉니다.
- `status`: `draft`(비공개 작성 중) → `published`(공개) → `closed`(정원 마감 등 수동 마감) / `canceled`(취소 표시)
- `visibility`: `public`만 웹에 노출됩니다. `private`는 캘린더에 나오지 않습니다.
- 날짜는 셀에 날짜·시간으로 입력합니다(시트 시간대는 서울). **날짜만 입력**하면 다음처럼 해석합니다.
  - `start_at`만 날짜 → 종일 이벤트
  - `registration_close`가 날짜만 → 그날 23:59까지 신청
  - `end_at`이 없으면 시작일 하루 동안 진행
- 신청 상태는 날짜로 자동 계산됩니다: COMING SOON(신청 전) · OPEN · CLOSED · FINISHED · CANCELED.
  - `registration_close`가 없으면 이벤트 시작 시각에 마감됩니다.
  - `registration_open`이 있어야 캘린더에 신청기간 점선이 그려집니다.
- `short_title`은 캘린더 칸에 들어가는 짧은 이름, `notes`는 준비물·안내, `public_fee`는 **공지용 참가비**입니다(제안자의 희망 금액과 별개).
- 시트를 고치면 1~2분 안에 웹에 반영됩니다.

### 회원 상태와 참여 권한 (ACTIVE MEMBERS ONLY)

Google 로그인만으로는 클럽 참여 권한이 생기지 않습니다. 상태는 `src/lib/access.ts`의 `memberAccess` **한 곳**에서만 계산하고, 화면·서버 처리·관리 화면이 모두 이것을 씁니다(Asia/Seoul 날짜 기준).

| 상태 | 뜻 | 참여 기능 |
|---|---|---|
| **ACTIVE** | 오늘이 확정된(승인된) 회원권 기간 안 | 허용 |
| **RENEWAL_DUE** | 아직 유효하지만, 그달 **마지막 7일** 동안 다음 달 1일이 확정 회원권으로 덮여 있지 않음 | 허용 + 갱신 안내 |
| **PENDING** | 입금·신청을 운영진이 확인 중 | 현재 회원권이 유효하면 그 기간까지만 허용, 아니면 차단 |
| **EXPIRED** | 유효한 회원권도, 확정된 연장도 없음 | 차단 |

- 장기 회원권(6+1, 12+2)과 선납은 실제 종료일로 판단합니다. 매달 납부 여부로 만료시키지 않습니다. 취소·환불된 회원권은 세지 않습니다.
- 확정됐지만 아직 시작 전인 회원권은 시작일부터 열립니다. 운영진(활성 operator/admin)은 회원권이 없어도 참여 기능을 쓸 수 있습니다.
- **차단되는 쓰기**: AFTER HOURS RADIO 선곡 등록(곡 정보 조회 포함), Host an Event 제안서 제출, MOON PROBLEMS 평가·완등 기록·후기(작성·수정·삭제). 서버 처리(`requireParticipant`)가 먼저 막고, 저장 규칙(`participantCheck`)이 같은 규칙으로 한 번 더 막습니다. 막히면 공통 코드 `MEMBERSHIP_REQUIRED`로 응답하고 화면은 같은 **MEMBERSHIP REQUIRED** 안내와 **REGISTER MEMBERSHIP**(→ 회원권 신청)을 보여 줍니다. *(Guestbook은 아직 이 사이트에 없는 기능이라 해당 없음. 새로 만드는 회원 쓰기 기능은 반드시 `requireParticipant`를 거칩니다.)*
- **허용**: 공개 페이지·일정·공지 열람, 회원권 상태 확인, 회원권 신청·동의서 확인(재등록), 받은 스탬프 보기·공유 이미지 만들기(읽기 전용), 알림 설정. 만료돼도 기존 기록(신청곡, 스탬프 등)은 지우지 않습니다.
- **회원이 아닌 계정**(Members에 없음)이 사이트에 넣을 수 있는 것은 **회원권 신청 하나뿐**입니다. 알림·푸시·동의서 확인은 Members에 있어야 하고, 데모 로그인은 실데이터에서 꺼져 있습니다. 새 계정의 미승인 신청이 20건 이상 쌓이면 새 계정의 신청을 잠시 받지 않습니다(가입 폭주 방지, 기존 회원의 재등록은 영향 없음).
- **상단 안내 배너**(홈·MY, 로그인한 본인에게만): 월말 7일 갱신 안내(RENEW YOUR MOON), 다음 달 입금 확인 중, 만료(MEMBERSHIP REQUIRED), 시작 전. 팝업이 아니라 닫을 수 있는 배너이고, 닫으면 그 기기에서 그달에는 다시 뜨지 않습니다.
- **CLUB NOTICE**(홈·MY, "아지트 공지"): 기본은 회비 납부(매월 말일까지 다음 달 회비, 선납 가능), 출입 비밀번호(단톡방에서만 안내 — **비밀번호는 사이트에 쓰지 않음**), 회원 단체 채팅방(유효 회원만). **admin이 관리 화면 → 설정 → 아지트 공지**에서 항목 제목·내용 수정, 추가·삭제(최대 8개), 순서 변경, 기본 문구로 되돌리기를 할 수 있고 저장 즉시 반영됩니다(미리보기 제공, 변경 이력 기록). 누구나 보는 공지라 계좌번호·전화번호처럼 보이는 숫자와 금액은 화면과 서버 모두에서 저장을 막습니다. 저장 위치: Settings `club_notice`(JSON), 없으면 기본 문구.
- **관리 화면 → 회원**: 상태(이용 중 / 갱신 예정 / 재등록 확인 대기 / 만료 / 시작 전)와 단톡방 확인 표시(정리 확인 · 초대 확인 · 재초대 확인), "단톡방 확인" 필터. 카카오톡 강퇴·초대와 출입 비밀번호 변경은 자동으로 하지 않고 운영진이 직접 처리하며, 이 표시는 할 일 안내일 뿐입니다.
- **사이트 이전부터 있던 회원**은 회원 상세의 **회원권 직접 등록**(입금 기록 없이, 사유 필수, 달 단위)으로 현재 이용 기간을 넣어 주세요. 넣지 않으면 그 회원은 만료로 보여 참여 기능이 막힙니다. 이 등록은 회비 수입으로 잡히지 않습니다.
- 데모에서 월말 화면을 보려면 `DEMO_TODAY=2026-11-26`처럼 날짜를 정해 실행합니다(데모 전용, 실데이터에서는 무시).

### 회원권과 회비

1. 회원이 로그인해 MY에서 회원권(기간)을 신청하면 Payments에 `pending`으로 기록됩니다. 회원 화면에는 "신청이 접수됐어요"와 안내 문구만 나오고, **계좌번호나 금액은 표시하지 않습니다.** 회원은 동의서와 단톡방 안내대로 회비를 냅니다. **승인 전에는 회원권이 생기지 않습니다.**
   - **첫 등록 가격**: 처음 등록하는 사람의 **1개월권은 100,000원**, 그다음부터는 80,000원입니다. Plans 탭의 `first_price`(첫 등록 가격)로 관리하며, 비어 있는 상품은 평소 가격 그대로입니다(6개월·12개월권은 기본으로 비어 있음). 금액은 운영진 화면에서만 쓰입니다. Payments의 `amount`에 받아야 할 금액이 기록되어 입금 확인, 거래내역 매칭, 회계 집계에 쓰이고, 금액이 그 상품의 `first_price`와 같으면 "첫 등록 가격"으로 표시됩니다(별도 열 없음). Plans에 `first_price` 열이 아직 없으면 평소 가격으로 동작합니다.
   - "첫 등록"은 한 번도 승인된 적이 없는 경우입니다. 사이트 이전부터 활동한 기존 회원은 Members 탭에 `joined_at`(가입일)만 적어 두면 평소 가격이 적용됩니다.
2. 운영진은 모임통장 앱에서 입금을 확인한 뒤 **ADMIN → 입금 확인**에서 승인합니다. **입금일은 제한 없이** 실제 날짜를 넣으면 되고(지난 날짜·앞 날짜 모두 가능), 기간에는 영향을 주지 않습니다. 시작 월은 필요할 때만 바꿉니다.
3. 승인하는 순간 Memberships에 기간이 생성되고, 회원 상태가 active로 바뀌며, 회원에게 알림이 갑니다.

**기간 규칙 — 달 단위** (Asia/Seoul 기준):
- 회원권은 **항상 1일에 시작해 말일에 끝납니다.** 날짜를 따로 고를 수 없고, 달만 고릅니다. 예: 11월 1개월권 → **11.01 – 11.30**, 12월부터 6개월권(+보너스 1개월) → **12.01 – 06.30**
- 총 기간 = `duration_months + bonus_months` (6개월권은 7개월, 12개월권은 14개월)
- **신규·만료 회원**: 회원이 신청할 때 고른 달에 시작합니다. 목록은 이번 달부터 4개월(기본은 첫 달)이고, 승인이 그 달보다 늦어지면 승인하는 달에 시작합니다.
- **새 회원권은 2026년 12월부터** 시작합니다(`src/lib/start-months.ts`의 `FIRST_START_MONTH`). 회원 신청 화면은 2026년 12월부터 4개월을 보여 주고, 운영진의 입금 승인 · 거래내역 승인 · 회원권 직접 등록의 월 선택도 2026년 12월부터 나옵니다. 승인 시 "자동"으로 계산된 시작이 그보다 이르면(예: 11월에 승인, 희망 시작 없음) 2026년 12월로 맞춥니다. 서버도 그보다 이른 시작을 거절합니다. **기존 회원권의 기간 수정, 회원 상세·이력은 그대로**라 예전 달도 보이고 고칠 수 있습니다.
- **연장**: 남은 회원권이 있으면 그 회원권이 끝난 다음 달 1일부터 이어지므로 남은 기간이 보존됩니다.
- 운영진이 승인할 때 **시작 월**을 직접 고르면 그 달 1일부터 시작합니다. 회원 상세의 기간 수정도 **시작 월 · 종료 월**로만 고칩니다.
- 이 규칙 이전에 만든 중간 날짜 회원권(예: 11.11 – 12.10)은 그대로 둡니다. 상태만 바꾸면 날짜는 유지되고, 달을 바꾸면 1일·말일로 맞춰집니다. 이런 회원권 뒤의 연장은 겹치지 않게 그다음 달 1일부터 시작합니다.

### 회원권 등록 계산 (MEMBERSHIP REGISTRATION, admin)

운영진(admin)이 여러 달을 한 번에 등록하고, 첫 달은 중간 날짜부터 시작하게 할 수 있습니다. **ADMIN → 회원 → 회원 상세 → MEMBERSHIP REGISTRATION**에서 씁니다.

1. **등록월 복수 선택**(이번 달·2026년 12월 중 늦은 달부터 13개월, 시간순 정렬, 이미 등록된 달은 "등록됨"으로 막힘) → **첫 등록월 시작일**(기본 1일, 그 달 말일까지 변경 가능) → 계산 내역과 **AMOUNT TO COLLECT**가 바로 바뀝니다(미리보기, 저장 안 됨).
2. **청구 만들기** → 입금 확인 대기 청구(Payments `pending`)만 생깁니다. **회원권은 아직 없고** 회원 화면에는 금액 없이 "운영진이 회원권 등록을 준비했어요"만 보입니다. 회원에게 금액은 단톡방 등으로 직접 안내합니다.
3. 입금을 확인하면 같은 자리(또는 입금 확인·거래내역 화면)에서 입금일을 넣고 **CONFIRM REGISTRATION**. 이때 회원권이 생깁니다.

- **계산식**: 월 회비 = 사용 중인 1개월 상품의 평소 가격(현재 80,000원). 첫 달 = `round(월 회비 × (그 달 일수 − 시작일 + 1) ÷ 그 달 일수)`(시작일·말일 포함, 원 단위 반올림), 이후 달 = 월 회비, 총 청구액 = 합계. 예: 12월 15일 시작 1개월 43,871원 · 12월+1월 123,871원 · 12~2월 203,871원 · 2027년 2월 15일 시작 40,000원. 첫 등록 가격(1개월 100,000원)은 이 계산에 적용하지 않습니다.
- **저장**: 청구 1건 = Payments 한 행(`amount` 총액, `requested_start` 첫날, `registration`에 `{"months":[…],"start":…,"fee":…}`). 확정하면 이어진 달끼리 묶어 Memberships 행을 만들고(떨어진 달은 각각, **사이 달은 이용 기간 아님**), 모두 `source_payment_id`로 그 청구와 연결됩니다. 한 커밋(트랜잭션)이라 일부만 저장되는 일이 없습니다.
- **중복 방지**: 회원당 입금 대기 청구·신청은 하나만, 이미 등록된 달은 다시 고를 수 없고(서버도 거절), 같은 화면에서 두 번 눌러도 같은 요청 번호라 한 번만 저장됩니다. 확정 시점에도 기간 겹침·금액 일치를 다시 확인합니다.
- **권한**: 계산·청구·확정은 **admin만**(화면과 서버 모두). 운영자(operator)에게는 확정 버튼이 잠겨 보이고, 회원 세션으로 직접 호출해도 거절됩니다. 청구 취소(반려)·승인 취소·환불은 기존과 같고 모두 AuditLog에 남습니다.
- **장기 상품**: 같은 화면에서 6+1·12+2 상품을 고르면 그 상품의 정해진 금액·기간(1일 시작, 보너스 포함)을 그대로 씁니다. 월 단위 계산과 섞이지 않습니다(6개월을 월 단위로 골라도 보너스 달 없음).
- 회원 카드의 "Valid until"은 끊김 없이 이어진 기간의 끝까지만 셉니다(예: 12월+1월+3월이면 1월 31일).

**수정·취소·환불**은 모두 AuditLog에 누가 언제 무엇을 바꿨는지(변경 전/후) 남습니다.
- 승인 취소: 회원권은 `canceled`로 남기고 입금은 다시 `pending`으로 돌립니다(올바른 조건으로 재승인 가능).
- 환불: 입금과 회원권을 `refunded`로 바꿉니다.
- 회원권 기간 수정: 회원 상세에서 시작 월·종료 월과 변경 사유를 입력합니다. 같은 회원의 다른 회원권과 겹치면 저장되지 않습니다.

### 사이트에서 결제를 요청하지 않는 이유

Vercel 무료(Hobby) 요금제는 비상업적 용도로만 쓸 수 있고, 상업적 이용의 예로 "사이트 방문자에게 결제를 요청하거나 처리하는 모든 방법"을 듭니다. 그래서 이 사이트는 **회원에게 계좌번호·금액을 안내하거나 입금을 요청하지 않습니다.** 사이트가 맡는 일은 일정, 회원권 신청과 조회, 운영진의 입금 확인 기록, 장부입니다. 회비 금액과 납부 방법은 회원 등록 동의서와 크루 단톡방에서 안내합니다. Settings 탭의 안내 문구에도 계좌번호나 금액을 넣지 마세요.

### 동의서

동의서는 크루의 Google 설문으로 받습니다. 응답은 Google Forms에 쌓이고, 사이트는 안내와 확인 기록만 맡습니다.

- **일일 이용 동의서**: 회원이 아닌 방문자가 방문하는 날마다 작성합니다. `/consent` 페이지에 모아 두었으니 카톡이나 출입구 QR로 공유하세요. 홈, 이벤트 상세, 푸터에서도 연결됩니다.
- **회원 등록 동의서**: 처음 회원권을 신청할 때 "Step 1"로 안내하고, "제출했어요"에 체크해야 신청됩니다. 체크한 시각은 Members 탭의 `member_consent_at`에 기록되고 AuditLog에도 남습니다. 사이트 이전에 등록한 기존 회원은 MY 화면에서 한 번 확인하면 됩니다.
- 운영진은 입금 승인 카드의 **동의서 ✓ / 동의서 미확인** 표시를 보고, 필요하면 Google Forms 응답에서 성함·연락처로 대조합니다(설문이 이메일을 수집하지 않아 자동 대조는 하지 않습니다).
- 설문을 새로 만들면 Settings 탭의 `consent_daily_url`, `consent_member_url`만 바꾸면 됩니다.

### 회계 (ADMIN → 회계)

클럽의 돈 흐름을 한곳에서 봅니다. 수입은 두 군데에서 모입니다.
- **회비**: 입금을 승인하면 자동으로 수입에 잡힙니다(Payments 기준이라 따로 적지 않습니다). 첫 등록 가격으로 받은 회비는 "(첫 등록)"으로 표시되고, 환불되거나 승인이 취소된 입금은 빠집니다.
- **그 밖의 모든 것**: 출자금, 일일 이용료, 이벤트 참가비, 그리고 모든 지출은 **Ledger 탭**에 기록합니다. 화면의 "기록 추가"를 쓰거나 시트에 직접 적어도 됩니다.

화면에서 보는 것:
- 지금 남은 돈, 총 수입, 총 지출, 보증금(돌려받을 돈)
- 월별 수입·지출과 월말 잔액, 항목별 지출·수입 순위, 출자자별 합계
- 기간·수입/지출 필터, CSV 내려받기(엑셀에서 한글이 깨지지 않게 BOM 포함)

기록은 지우지 않고 **무효 처리**합니다. 수정과 무효 처리에는 사유가 필요하고, 모두 AuditLog에 남습니다.

**기존 회비 사용 내역 옮기기:** `private/ledger-import.xlsx`(Git 제외)에 기존 시트를 Ledger 형식으로 바꿔 두었습니다. 잔액이 원본의 차액과 같은지 확인했습니다. 실데이터 시트의 Ledger 탭 2행부터 그대로 붙여넣으면 됩니다. 출자금은 원본에 날짜가 없어 첫 지출일로 넣었고, "계약비"는 보증금의 일부(계약금)로 분류했으니 확인해 주세요.

### 이벤트 포스터 (MAKE A POSTER)

운영진(operator/admin)으로 로그인하면 이벤트 상세 위쪽에 **Make a poster** 버튼이 보입니다. 누르면 그 이벤트의 현재 공개 정보로 브랜드 포스터를 만들고, 규격을 골라 **Save PNG**로 저장합니다.

- 규격: **FEED 1080×1440 (3:4)**, **STORY 1080×1920 (9:16)**. 규격마다 레이아웃이 따로 있고(자르거나 늘리지 않음), STORY는 인스타그램 화면 요소를 피해 위아래 여백을 둡니다.
- 들어가는 정보: 공식 로고, 카테고리, 날짜·요일·시간(Asia/Seoul), 제목, 장소, 참가비, 준비물, `#afterc2m`, 사이트 주소. **시트에 없는 항목은 빠지고, 임의로 채우지 않습니다.**
- 제목은 자르지 않습니다. 길면 글자를 줄이고 줄을 늘립니다. 자리가 모자라면 준비물(BRING)을 먼저 줄이거나 뺍니다.
- 취소된 이벤트는 버튼이 보이지 않고, 주소로 직접 열어도 CANCELED 표시가 들어간 미리보기만 나오며 저장은 막혀 있습니다.
- 이벤트를 고친 뒤 다시 열면 최신 정보로 다시 만들어집니다(시트에서 직접 고친 내용은 1~2분 뒤, ADMIN에서 고치면 바로).
- 모든 렌더링은 브라우저 안에서 끝납니다. 이미지 서버나 AI API를 부르지 않아 추가 비용이 없습니다. 휴대폰에서는 공유 화면의 "이미지 저장"으로 사진첩에 저장됩니다.
- 디자인을 바꾸려면 `src/lib/canvas/poster.ts`의 `LAYOUTS`와 `drawPoster`를 고칩니다(템플릿은 한 종류).

### MOON STAMPS

클럽에서의 순간을 멤버 개인의 기념 스탬프(디지털 패치)로 남깁니다. 포인트·랭킹·보상이 아니라 기록과 소장이 목적입니다.

| ID | 이름 | 발급 조건 |
|---|---|---|
| ST-01 | FIRST MOON | 첫 클럽 방문 |
| ST-02 | 100 HOLDS | 100홀드 지구력 문제 완등 — 운영진이 지정한 100개 홀드짜리 지구력 문제 **하나**를 완등. 누적 완등 100회·서로 다른 문제 100개·기간에 걸친 홀드 누적이 아님 |
| ST-03 | NIGHT OWL | 퇴근 후 클럽 세션 참여 |
| ST-04 | MOON HOST | 직접 이벤트 개최 |
| ST-05 | SIX MOONS (6 + 1 MONTHS) | 6+1개월 회원권 등록 (누적 이용 6개월과 별개) |
| ST-06 | TWELVE MOONS (12 + 2 MONTHS) | 12+2개월 회원권 등록 (누적 이용 12개월과 별개) |

- **발급은 운영진이 직접 확인해서 합니다.** 자동 판정·출석 체크·홀드 집계·회원권 연동 자동 발급은 없습니다. **ADMIN → 회원 → 회원 상세 → Moon stamps**에서 발급일(오늘 또는 지난 날짜)과 비공개 메모를 넣고 **스탬프 발급**을 누르면 됩니다. 100홀드 문제의 루트와 판정 기준은 운영진이 따로 관리합니다(MOON PROBLEMS와 연결하지 않음).
- SIX MOONS·TWELVE MOONS 칸에는 그 회원의 **6+1 / 12+2 회원권 등록 기록**(취소·환불 제외)이 참고로 보입니다. 참고일 뿐이고, 기록이 없어도 운영진이 확인했다면 발급할 수 있습니다.
- **종류별로 한 번만** 발급됩니다. 두 운영진이 동시에 눌러도 한 건만 기록됩니다. 잘못 발급했다면 **발급 취소**(사유 필수)로 되돌립니다. 기록은 남고 다시 발급할 수 있습니다.
- 회원은 **MY → My Moon Stamps**에서 6종을 보고(받은 것은 날짜와 함께, 아직인 것은 흐리게), 받은 스탬프를 누르면 상세가 열립니다. **아직 받지 않은 스탬프에는 공유 버튼이 없습니다.**
- **Instagram 공유:** 상세의 **SHARE THIS STAMP** → **STORY**(1080×1920, 9:16) 또는 **FEED**(1080×1440, 3:4)를 고르면, 서버가 먼저 그 회원이 정말 그 스탬프를 받았는지 확인한 뒤 브라우저가 해당 규격 전용 레이아웃으로 PNG를 그립니다(공식 로고, 스탬프 그림, 이름·보조 문구·영문 문구·설명, `EARNED AT AFTER CL TO MOON`, 받은 날짜가 있을 때만 날짜, `#afterc2m`). 파일 공유를 지원하는 기기(`navigator.canShare`)에서는 **공유하기**로 OS 공유 시트를 열고, 아니면 **PNG 저장**으로 내려받습니다. 공유를 취소하면 성공으로 표시하지 않고, Instagram 게시를 대신하거나 보장한다고 표현하지 않습니다. **이미지에는 이름·이메일·회원번호가 들어가지 않습니다.** 서버 호출은 읽기만 하고(기록 없음), 외부 AI·이미지 API는 쓰지 않습니다.
- 스탬프 그림 6종은 완성된 정적 에셋입니다(`public/stamps/st-0N.svg`). 글자는 사이트 폰트를 외곽선으로 바꿔 넣어 어디서나 같게 보입니다. 디자인을 고칠 때만 `scripts/stamps/build-stamps.mjs`를 수정하고 `npm run stamps:build`로 다시 만듭니다(스탬프마다 고정 시드라 하나를 고쳐도 다른 그림은 바이트 단위로 그대로).
- DB: **StampDefinitions**(stamp_id, name, description, image_key, active)는 **관리 화면 → 설정 → MOON STAMPS**에서 문구를 바꾸거나 끌 수 있습니다(이미 받은 회원에게는 계속 보임). 행이 없으면 코드 기본값을 씁니다. ST-01~06 외의 행은 무시합니다. **StampAwards**(award_id, member_id, stamp_id, awarded_at, awarded_by, note)는 발급 기록입니다.
- v1.4 데이터 반영(선택): `npm run db:v14-stamps`(미리보기) → `npm run db:v14-stamps -- --apply`. ST-02 정의 행이 아직 `FIRST TOP`일 때만 100 HOLDS로 바꾸고(운영진이 이미 고친 문구는 그대로), ST-05·06 행이 없으면 추가합니다(감사 로그 포함, 다시 실행해도 안전). **기존 ST-02 발급 기록은 바꾸지 않고** 운영진 확인용으로 목록만 보여 줍니다.

### MOON PROBLEMS (`/problems`)

SET BY US. CLIMBED BY US. — 문제는 벽에서 만들고, 기록은 웹에 남깁니다. 텍스트만 다루는 작은 볼더링 문제 도감입니다(사진·홀드 표시·온라인 세팅·AI 없음). 홈의 MOON PROBLEMS 섹션(최근 ACTIVE 3개)과 푸터의 **Problems**로 들어갑니다(상단 메뉴는 그대로).

- **누가 무엇을**: 누구나 목록·상세·후기를 봅니다. **운영진(operator·admin)** 만 문제 등록(`/problems/new`)·수정(`/problems/번호/edit`, Setter's Note·Beta 포함)·보관·삭제·복구와 후기 숨기기를 합니다. **회원권이 유효한 회원**(운영진 포함)만 평가를 남기고 고치고 지웁니다. 화면에서 버튼을 숨기는 것과 별개로 모든 쓰기를 서버가 다시 확인합니다(운영진은 매번 DB를 새로 읽어 확인).
- **문제**: 번호(MOON 001…)는 자동으로 다음 번호가 붙고 다시 쓰지 않습니다(DB 유니크 인덱스). 난이도는 클럽 색깔 체계 7단계에서 고릅니다: **빨강 (5.8 이하 ~ 5.9, 입문) → 주황 (5.9 ~ 5.10b, 초급) → 노랑 (5.10b ~ 5.10d, 초중급) → 초록 (5.10d ~ 5.11b, 중급) → 파랑 (5.11b ~ 5.11d, 중상급) → 보라 (5.11d ~ 5.12c, 상급) → 검정 (5.12d 이상, 고급~엘리트)**. 저장은 색 이름, 표시는 "노랑 (5.10b ~ 5.10d)". 목록 필터·정렬도 이 순서이고, 서버는 이 일곱 가지 외 값은 받지 않습니다(`src/lib/problems.ts`의 `GRADES`). 상태는 ACTIVE / ARCHIVED / 삭제(소프트 삭제: 행과 후기는 남고, 운영진은 목록 아래에서 되살릴 수 있음). 보관된 문제는 기존 기록을 그대로 보여 주고 새 평가는 받지 않습니다.
- **평가(RATE THIS PROBLEM)**: 재미 1~5, 체감 난이도 EASY/FAIR/HARD, SENT/PROJECTING, 한 줄 후기(200자). **회원당 문제별 1건**: 다시 저장하면 수정되고(PROJECTING → SENT 포함), 지웠다가 다시 쓰면 같은 행을 재사용합니다. DB에도 `problem_reviews (problem_id, member_id)` 유니크 인덱스가 있어 중복 행이 생길 수 없습니다. 완등은 자기 신고입니다.
- **통계**: 유효한(지우거나 숨기지 않은) 평가만으로 계산합니다. 완등 인원 = SENT 수, 평균 재미 = 실제 평가 평균(소수 첫째 자리), 체감 난이도 분포. 평가가 없으면 0점 대신 "아직 평가가 없습니다".
- **후기 관리**: 운영진이 부적절한 후기를 숨기면 공개 화면과 통계에서 빠지고, 작성자는 다시 살릴 수 없습니다(운영진은 "다시 보이기" 가능).
- DB: `problems`, `problem_reviews` 테이블(운영 DB 반영은 `npm run db:migrate -- --schema-only`). 모든 변경은 AuditLog에 남습니다.

### AFTER HOURS RADIO (`/radio`)

멤버들이 함께 만드는 음악 목록입니다. 홈 아래 **Tune in**이나 푸터의 **Radio**로 들어갑니다(상단 메뉴는 그대로).

- **목록**: 기본곡 14곡 다음에 신청 순서대로 쌓입니다. 누구나 볼 수 있지만, **멤버 신청곡의 신청자 이름과 사연은 로그인한 회원에게만** 보입니다(로그아웃 상태에서는 "멤버 신청"으로 표시). 기본곡의 표시 이름과 운영진 메모는 모두에게 보입니다. 목록은 약 20초마다 새로 고쳐집니다.
- **트랙 관리(ADMIN → 라디오)**: 재생 순서(▲▼ 한 칸씩), 곡명·아티스트, **표시 이름(display_name)**, **메모(message: 신청자의 사연이나 운영진 메모)** 를 고치고, 곡을 삭제하거나 **삭제한 곡을 원래 자리로 되돌릴** 수 있습니다. **운영진(operator·admin)** 이 할 수 있습니다. 모든 변경은 AuditLog에 남고, 그사이 다른 사람이 같은 곡을 고쳤다면 저장되지 않습니다. 같은 영상이 이미 목록에 있으면 되돌리기를 막습니다.
- **신청(ADD A TRACK)**: 로그인한 회원(Members 탭, 이용 중지 제외)만 할 수 있습니다. YouTube 링크(youtube.com/watch, youtu.be, shorts, music.youtube.com 등)를 붙여넣으면 곡명·아티스트를 YouTube oEmbed로 채워 주고, 회원이 고칠 수 있습니다. **이름**(목록에 보이는 신청자 이름, 회원 이름이 미리 채워짐, 비우면 회원 이름, 40자까지)과 **메모·한 줄 사연**(150자까지, 선택)도 함께 받습니다. **승인 없이 바로 목록 끝에 추가**되고 시트에 저장됩니다. 같은 영상이 이미 있으면 막고 몇 번째 곡인지 알려 줍니다. 없는 영상(비공개·삭제)은 받지 않습니다.
- **삭제(DELETE TRACK)**: **운영진(operator·admin)** 에게만 보이고 할 수 있습니다. 라디오 화면과 ADMIN → 라디오 양쪽에서 할 수 있습니다. 서버가 Members 탭으로 권한을 다시 확인하고, 행을 지우지 않고 `status = deleted`, `deleted_at`, `deleted_by`만 기록합니다. 삭제된 곡은 목록·재생 순서에서 빠지고, 재생 중이던 곡이면 공용 플레이어가 다음 곡으로 넘어갑니다. 삭제한 곡을 다시 신청하는 건 가능합니다.
- **플레이어**: 아지트의 공용 기기 한 대에서 이 페이지를 열어 두는 방식입니다. YouTube IFrame 플레이어(youtube-nocookie)로 목록 순서대로 재생하고, 이전/다음 곡, 반복(전체·한 곡), 곡별 재생, **셔플**을 지원합니다. 셔플은 모든 곡을 한 번씩 무작위 순서로 돈 뒤 다시 섞고(UP NEXT에 섞인 순서가 보임), 이전 곡은 실제로 들었던 곡으로 돌아가며, 셔플 중 새로 신청된 곡은 남은 순서 사이에 무작위로 끼어듭니다. 셔플 켜짐 여부와 마지막 곡은 그 기기에 기억됩니다. 재생할 수 없는 영상은 원본 링크를 보여 주고 다음 곡으로 넘어갑니다. 새 신청곡은 지금 곡을 끊지 않고 목록 끝에 붙습니다. 다른 사람의 기기를 조작하는 기능은 없습니다.
  - **플레이어는 기본으로 꺼져 있습니다.** 공간에서 음악을 함께 트는 것은 이용 권한(YouTube 약관, 공연권 등)을 확인한 뒤 켜기로 했습니다. 확인되면 Settings 탭의 `radio_player`를 `on`으로 바꾸세요. 꺼져 있는 동안에도 목록·신청·삭제는 그대로 되고, 각 곡의 YouTube 링크로 들을 수 있습니다.
- **기본곡 14곡**: 곡마다 제목·아티스트로 찾아 **공식 업로드를 우선** 연결했고, YouTube 플레이어에서 실제 재생되는 것을 확인했습니다(2026-11-12, 목록은 `src/lib/radio.ts`). 단, **RIDE ON TIME은 YouTube에 공식 전곡 업로드가 없어** 조회수가 가장 많은 팬 업로드를 연결했습니다. 내려갈 수 있으니 필요하면 삭제하고 다른 링크로 신청하세요.
  - 기본곡은 `setupSheets`가 **RadioTracks 탭을 처음 만들 때 한 번만** 넣습니다. 다시 실행하거나 사이트를 다시 배포해도 추가·복원되지 않으므로, 삭제한 기본곡은 삭제된 채로 남습니다.
- 시트 **RadioTracks**: track_id, title, artist, youtube_url, youtube_video_id, requested_by(회원 ID 또는 AFTER CL TO MOON), display_name, message, source(seed/member), sort_order, created_at, status(active/deleted), deleted_at, deleted_by. 순서를 바꾸고 싶으면 `sort_order`를 고치면 됩니다.

### 거래내역 엑셀 매칭 (ADMIN → 거래내역)

카카오뱅크 앱에서 모임통장 거래내역을 엑셀로 내려받아 올리면, 입금만 골라 신청 내역과 비교합니다.
- **일치**: 입금자명과 금액이 한 건과 정확히 맞음 → 확인 후 승인
- **확인 필요**: 동명이인(같은 이름·금액 여러 건), 부분 입금·금액 다름, 대리 입금(금액만 같음)
- **반영됨**: 이미 승인에 쓰인 거래. 같은 파일을 다시 올려도 두 번 반영되지 않습니다(거래 키 = 거래일시·금액·잔액·입금자명의 해시).
- 파일은 서버 메모리에서 읽기만 하고 **저장하지 않습니다.**

> ⚠️ 파서는 열 이름(거래일시·거래금액/입금액·구분·내용·거래 후 잔액 등)으로 머리글을 찾도록 만들었지만, **실제 모임통장 내보내기 파일로는 아직 검증하지 않았습니다.** 개인정보를 가린 실제 파일 한 개로 확인한 뒤 필요하면 열 이름을 보완해야 합니다(`src/server/domain/bank.ts`의 `ALIASES`).

## 보안과 개인정보

- 브라우저는 시트에 직접 접근하지 않습니다. 모든 읽기·쓰기는 서버에서 비밀키로 Apps Script를 호출합니다.
- 로그인은 Google OIDC(PKCE·state·nonce 검증)로 하고, 세션은 서명된 httpOnly 쿠키에 저장합니다. **권한(member/operator/admin)은 매 요청 Members 시트로 다시 확인합니다.** 승인·수정 같은 처리는 항상 실시간 시트로 확인하므로 시트에서 권한을 바꾸면 즉시 막히고, 관리 화면 보기에는 최대 1분 뒤에 반영됩니다.
- 회원 화면은 로그인한 본인 데이터만 조회합니다(URL에 회원 ID를 받지 않음). 운영진이 아니면 관리 화면은 404로 보입니다.
- **이벤트 제안(`/host`)은 로그인한 사용자만** 쓸 수 있습니다. 로그인하지 않으면 `src/proxy.ts`가 로그인 화면으로 보내고, 로그인 후 제안 페이지로 돌아옵니다. 페이지와 제출 처리는 서버에서 세션을 다시 확인하므로, 쿠키를 꾸며 내거나 제출 요청을 직접 보내도 저장되지 않습니다. 이름과 연락처(로그인 메일)는 미리 채워집니다.
- **스탬프 발급 기록은 공개 API로 나가지 않습니다.** 회원 화면은 로그인 세션을 Members 탭으로 확인한 본인의 스탬프만 서버에서 골라 보내고(요청에서 회원 ID를 받지 않음), 발급자와 운영진 메모는 보내지 않습니다. 전체 기록은 운영진 화면에서만 보입니다.
- **라디오 신청·삭제는 서버에서만** 시트에 씁니다. 신청자는 로그인 세션을 Members 탭으로 확인해 정하고(브라우저가 보낸 회원 ID나 역할은 믿지 않음), 삭제는 admin인지 실시간 시트로 다시 확인합니다. 화면과 `/api/radio`에는 회원 ID가 나가지 않고, 이름·사연은 로그인한 회원에게만 갑니다.
- 웹에서 시트에 쓰는 모든 텍스트는 일반 텍스트로 저장되어 수식이나 숫자로 해석되지 않습니다.
- 서비스 워커는 페이지를 캐시하지 않아, 공용 기기에서 다른 사람의 회원 정보가 남지 않습니다.
- 데모 로그인은 시트가 연결되면 자동으로 꺼집니다.

## 알려진 제한

- Notifications·AuditLog 탭은 계속 쌓입니다. 1년에 한 번 정도 오래된 행을 다른 시트로 옮겨 보관하는 것을 권장합니다.
- Apps Script 호출은 한 번에 약 1.6초, 읽는 탭마다 약 0.3초가 더 걸립니다(데이터 양과 거의 무관). 회원 화면은 30초 서버 캐시로, 운영진 화면은 모든 관리 탭이 함께 쓰는 1분 캐시(필요한 탭 8개를 한 번에 읽음)로 보완합니다. 사이트에서 무언가 저장하면 두 캐시 모두 즉시 비워지고, 모든 쓰기와 처리 직전 확인은 항상 실시간 시트를 기준으로 합니다. 시트에서 직접 고친 내용은 관리 화면에 최대 1분 늦게 보입니다.
- 접근 권한이 없는 관리 화면은 404 화면을 보여주지만, 스트리밍 렌더링 특성상 HTTP 상태 코드는 200입니다(내용은 노출되지 않음).
